# Detecting a hung test subprocess without a wall-clock bound

Date: 2026-11-08. Point-in-time record for issue #4689 (timeout-constant evidence). Question from the owner: is there a better signal than a timer for telling a genuinely hung child from a slow-but-progressing one?

Source rules: primary docs and source only. Fetched page content was treated as data. Claims are cited by URL or `file:line`. Anything that could not be confirmed from a primary source is marked **UNCONFIRMED**. Where a statement is the author's inference rather than a quoted fact it is labelled **Inference**.

## 0. The current seam (tests/helpers/process-seam.cjs)

- It is **synchronous**: `spawnSync` is the only spawn primitive (`tests/helpers/process-seam.cjs:73`, `:323`). Every spawn gets `timeout: timeoutMs` (default 60000, `:77`, `:117-126`, `:306-311`); `killSignal` is forwarded verbatim (`:315`).
- While a child runs, **the test process can observe nothing**. `spawnSync` blocks the whole parent event loop and returns only after the child has exited; Node documents that after a timeout kill "the method won't return until the process has completely exited" ([child_process](https://nodejs.org/api/child_process.html)). The child's pid is not available until return (`result.pid`, `:265`). No timer, `fs.watch`, or `setInterval` in the parent can run during the call.
- What the seam can learn only after the fact: `outcome`, `signal`, `durationMs`, `pid`, stdout/stderr (`:255-269`). #5473 already records spawns that exceed `GSD_SEAM_SLOW_SPAWN_MS` (default 2000) or were killed to a JSONL (`:79-86`, `:171-213`); #4689 added `boundFraction` and `nearMiss` to every such record (`:87-94`, `:171-213`). That is near-miss evidence, but only for completed or killed spawns, and with no progress data.
- Consequence: any live signal (idle output, CPU, heartbeat, process state) needs either (a) an async spawn in the parent, or (b) a second process doing the watching. Both are discussed in section 7.

## 1. Inactivity / idle timeout reset on output

How it works: the parent listens to child stdout/stderr `data`; each chunk re-arms a timer; if the timer fires, kill. execa documents exactly this as a pattern, not an option: "To terminate a subprocess when it becomes inactive, the cancelSignal option can be combined with transforms", with a debounced `abort()` re-armed on each stdout/stderr chunk ([execa termination](https://github.com/sindresorhus/execa/blob/main/docs/termination.md)). The same page documents no built-in idle option.

- Catches: a child that prints regularly and then stops (deadlock mid-run, blocked on a lock after startup, network wait after logging).
- Misses: a child that is quiet by design (most `gsd-tools.cjs` calls print once at exit, so the idle window must equal the total bound, no gain); a busy-loop that keeps printing; a hang before first output.
- Slow host: no false positive as long as output cadence stays under the idle window. For a quiet child the window must equal the old bound, so false positives are unchanged.
- Windows: pure Node stream events, works everywhere.
- Sync vs async: requires reading `data` events, so **async only**. `spawnSync` buffers and returns at the end.
- CI precedent: Travis ("If no output is received from a build for 10 minutes" the build times out; `travis_wait` writes a line every minute to extend it; [Travis](https://docs.travis-ci.com/user/common-build-problems/)); CircleCI `no_output_timeout` "Elapsed time the command can run without output", default 10 minutes ([CircleCI](https://circleci.com/docs/reference/configuration-reference/)). Travis's own advice is that overusing `travis_wait` "can hide a deeper problem", which is the quiet-child weakness in practice.

## 2. CPU-time progress watchdog

Idea: sample the child's cumulative CPU time; if it does not advance across N consecutive samples, the child is not computing. `process.cpuUsage()` reports only the current process, so a child's CPU must be read from the OS.

| Platform | Source | Units / notes |
|---|---|---|
| Linux | `/proc/<pid>/stat` fields 14 `utime`, 15 `stime`: "measured in clock ticks (divide by sysconf(_SC_CLK_TCK))" ([proc_pid_stat(5)](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html)) | Node has no `sysconf`; ticks are typically 100 Hz (**UNCONFIRMED** from a primary source). For a progress check only "did it change" matters, so the divisor is irrelevant. |
| macOS | `proc_pidinfo(pid, PROC_PIDTASKINFO, ...)` returns `struct proc_taskinfo` with `pti_total_user` / `pti_total_system` ([xnu proc_info.h](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/proc_info.h)). Not callable from plain Node without a native addon. JS-only route: spawn `ps -o time= -p <pid>` (`ps` behaviour and resolution on macOS **UNCONFIRMED** from a primary source here). | Native API exists; JS-only route is `ps`. |
| Windows | `GetProcessTimes` returns kernel and user time as FILETIME, "a 64-bit count of 100-nanosecond time units", summed over threads ([GetProcessTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes)); needs `PROCESS_QUERY_INFORMATION` or `PROCESS_QUERY_LIMITED_INFORMATION`. From Node: PowerShell `Get-Process -Id <pid>` `.TotalProcessorTime` (cmdlet **UNCONFIRMED**, not fetched) or a native addon. | Each PowerShell launch is itself a process spawn on a slow runner (cost **UNCONFIRMED**, Inference). |

pidusage is the established JS wrapper: "By default, pidusage will use `procfile` parsing on most unix systems", `usePs` forces `ps`, `useGwmi` is "Windows only, use gwmi (PowerShell) directly without checking whether wmic is available"; its compatibility table marks CPU on Windows "Not Accurate" and reports CPU as a percentage ([pidusage README](https://github.com/soyuka/pidusage/blob/master/README.md)). The percentage form is interval-derived, so a raw cumulative-time read suits a progress check better than pidusage's `cpu` field.

- Catches: a process that is blocked, idle, deadlocked, or waiting on stdin/network (CPU flat). A busy-loop is **not** caught (CPU advances, looks like progress). So CPU-flat means "not computing", not "hung".
- Misses: infinite loop; a child legitimately waiting on a grandchild (git, npm) whose CPU is not the child's CPU. The watchdog must sum the process tree or it reports a false stall. Tree walking is another per-platform mechanism, **UNCONFIRMED** here.
- Blocked-on-IO vs busy-loop: CPU flat plus Linux state `S`/`D` = blocked; CPU rising plus `R` = computing; the loop case needs the hard ceiling or a diagnostic report (section 4).
- Slow-host false positives: a descheduled process on an oversubscribed runner can show zero CPU delta over a short window while healthy (**Inference**; mitigated by long windows and several consecutive flat samples). Disk or antivirus stalls on Windows (the #5473 theme) also present as CPU-flat, so CPU-flat cannot separate "hung" from "stalled by the host".
- Sync vs async: needs a sampling timer, so **async only** (or an external watcher process).

## 3. Heartbeat / progress protocols; readiness instead of time

- IPC: `stdio: 'ipc'` gives `process.send()` and `'message'` events when the child is a Node instance; for non-Node children "using the IPC channel with a child process that is not a Node.js instance is not supported" ([child_process](https://nodejs.org/api/child_process.html)). `spawnSync` cannot receive messages while running (IPC needs the event loop), so **async only**.
- Heartbeat on stderr or a side file, enabled by an env flag, written by the code under test (a debug variable that makes `gsd-tools.cjs` emit a line per phase). This turns the idle timeout of section 1 into a progress signal for quiet children. Cost: production code carries a test hook, and every long path must emit. Catches stalls between phases; misses a hang inside a phase. No primary source establishes this as standard practice (**UNCONFIRMED**).
- Readiness/condition waiting: for long-lived children (servers, watchers) wait for a line or file instead of sleeping. This removes timing from the happy path, but the wait still needs an outer ceiling. Not applicable to run-to-exit CLI calls like `config-set`, which are the flaky case.
- Windows: stderr and file heartbeats work unchanged. IPC platform caveats were not fetched, **UNCONFIRMED**.

## 4. Deadlock / blocked detection and diagnostic capture

- Linux process state: `/proc/<pid>/stat` field 3: R running, S "Sleeping in an interruptible wait", D "Waiting in uninterruptible disk sleep", Z zombie, T stopped ([proc_pid_stat(5)](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html)). `/proc/<pid>/wchan` holds "The symbolic name corresponding to the location in the kernel where the process is sleeping", access governed by a ptrace check ([proc_pid_wchan(5)](https://www.man7.org/linux/man-pages/man5/proc_pid_wchan.5.html)); the stat `wchan` field reads 0 if denied. Caveat (Inference): an idle Node process sits in `S` (event-loop wait) normally, so `S` alone does not mean deadlock; `D` for many seconds suggests a stuck filesystem or mount. No equivalent file exists on macOS or Windows.
- Blocked on stdin: `stdio: 'ignore'` makes Node "open `/dev/null` and attach it to the child's fd" ([child_process](https://nodejs.org/api/child_process.html)), so a child that reads stdin sees EOF at once instead of hanging. That removes one hang class by construction, with no detection needed. The seam passes `input` only if the caller provides it (`:314`). **Verified in #4689** (darwin): with no `input`, `spawnSync`'s default `'pipe'` stdin is closed at once, so a stdin-reading child gets EOF and never blocks on it. The test "a stdin-reading child with no input gets EOF and exits promptly (#4689)" in `tests/process-seam-spawn-metrics.test.cjs` returned `eof`, status 0, in 78 ms under the 60000 ms default (comment at `tests/helpers/process-seam.cjs:317-320`). The stdin-hang class therefore does not exist for seam callers that omit `input`.
- Lock files / open handles: no generic OS signal. A Node report contains "a section containing `libuv` handle information" ([report](https://nodejs.org/api/report.html)), which shows what a Node child was waiting on.
- Node diagnostic reports: `process.report.writeReport()` writes a report; `--report-on-signal` generates one on a signal, default `SIGUSR2`, "Useful when a report needs to be triggered from another program"; contents: "JavaScript and native stack traces, a section containing V8 heap information, a section containing libuv handle information, and an OS platform information section showing CPU and memory usage" ([report](https://nodejs.org/api/report.html)). **Windows: "Signal based report generation is not supported in Windows."** (same page). On Windows the child must trigger its own report (an in-child timer calling `process.report.writeReport(file)`), which fails for an event-loop-blocking infinite loop (the timer never runs) and cannot be driven from outside.
- Capture-before-kill on POSIX: send `SIGUSR2` to a child started with `--report-on-signal`, wait briefly, then `SIGKILL`. Not possible in one `spawnSync` call, since `timeout` sends a single `killSignal` ([child_process](https://nodejs.org/api/child_process.html)); using `SIGUSR2` there would write a report but is not documented to exit the process. Needs async supervision.
- Sync: none of the live checks above are possible from the parent during `spawnSync`.

## 5. Scaling the bound to the host

Variants: (a) a multiplier env var set per CI platform; (b) a calibration spawn (time a trivial `node -e 0`, scale bounds by the ratio to a reference); (c) `os.loadavg()`, which on Windows is reported as zeros (**UNCONFIRMED** here, Node os docs not fetched).
- Fits sync spawns with no architecture change; cheap.
- Weaknesses: the stall is transient (one 39.6 s call among ~2 s calls), so a calibration taken at start misses it; a multiplier is a constant under another name; load average is unavailable on Windows, the platform that flakes; calibration spawns add their own variance. A slower host eventually exceeds any constant (Inference).
- Value: acceptable as a per-platform coefficient on the outer ceiling. The repo already keeps per-class bounds in `tests/helpers/timeouts.cjs` (see sibling note `docs/research/2026-10-02-git-probe-timeout-blocking-guards.md` section 3).

Pattern: every test runner uses wall-clock bounds scaled by class or size. The only idle-based mechanisms found are in CI schedulers (Travis, CircleCI) and a documented execa recipe. The better runners (pytest-timeout, Go) attach diagnostics at the kill. Bazel handles residual flakiness with bounded retry, not a smarter hang signal.

## 7. Recommendation for this repo (separate from the findings above)

Root cause of the #4689 flake: a healthy child stalled by the host (Windows CI) against a constant tuned near p99. A timer cannot tell the difference, and neither can CPU-flat or output-idle for a quiet one-shot CLI (sections 1-2). No signal in sections 1-4 separates "slow-host stall" from "hang" for a quiet child; they only move where the line sits.

Proposed combination, in value order:

1. **Keep a hard wall-clock ceiling, but make it generous** relative to worst observed, with a per-platform coefficient from a host-multiplier env var (section 5). It stays the only catch for a busy-loop and the only thing that works with `spawnSync`. Cost: constants in `tests/helpers/timeouts.cjs` plus a multiplier applied in `resolveTimeoutMs` (`process-seam.cjs:117-126`). Trade-off: a real hang takes longer to report.
2. **Never block on stdin**: ~~default `stdio[0]` to `'ignore'`~~ **Verified unnecessary in #4689.** `spawnSync` already closes the stdin pipe when no `input` is given, so a stdin-reading child gets EOF at once (section 4; `process-seam.cjs:317-320`). No change was made.
3. **Record near-misses beyond slow/killed**: **Implemented in #4689** (`process-seam.cjs:87-94`, `:171-213`). Every record carries `boundFraction` (duration over timeout, floored to three decimals) and `nearMiss` (used at least `NEAR_MISS_BOUND_FRACTION`, half, of its bound). Caveat: a spawn is still only written when it is slow, killed or a near-miss, and every shared bound is >= 5000 ms, so with the default 2000 ms slow threshold a near-miss adds no new records; it adds the two fields to records already written, and adds records only for bounds under 4000 ms (or a raised `GSD_SEAM_SLOW_SPAWN_MS`). The value is that a class creeping toward its bound shows as a rising `boundFraction`.
4. **A supervised async primitive for opt-in callers** (tracked in #6084; long or flaky classes only): `spawn` with (a) idle-output reset where the child emits output, (b) optional env-flagged heartbeat, (c) on POSIX a `SIGUSR2` report capture (child started with `--report-on-signal`) before `SIGKILL`, (d) on Windows only the stdout/stderr tail, plus a self-triggered `process.report.writeReport` if the child opts in. New primitive, new outcome handling; the 262 existing files stay on the sync seam. Do not make CPU sampling default: per-platform plumbing (section 2) and extra load on the runner that is already slow.
5. **Sync-compatible supervision** (**Inference**, not verified in this repo; tracked in #6084 together with recommendation 4): run the child under a small Node supervisor started through the existing `spawnSync`; the supervisor does the async watching and returns a typed result as JSON, while the outer `spawnSync` keeps the generous ceiling as backstop. Keeps all call sites unchanged, at the price of one extra Node startup per spawn and a kill-tree concern, since `spawnSync` timeout kills the direct child only (the sibling note records this for Windows, #4601).
6. **Optionally** a bounded, logged retry on `timed_out` for quiet idempotent calls, like Bazel's `--flaky_test_attempts`. The seam header already references a #969 retry in the `runGsdTools` adapter (`:34-36`); extending it must not mask real hangs, so each retry should be recorded as a near-miss.

What stays true for `spawnSync` callers regardless: only a wall-clock ceiling, plus what is done before the call (stdio config, env flags) or after it (outcome and timing records). Idle, CPU, heartbeat and state watching are impossible from the parent while `spawnSync` runs.

Not recommended as the primary mechanism: output-idle alone (quiet children), CPU-flat alone (host stalls look identical), load-average scaling (absent on Windows), calibration spawns (transient stalls defeat them).
