# Bracket phase IDs

> Reference. Behavior of `phase_id_convention: "bracket"` across read, display, migration and write
> paths. The key and its values are in [Configuration](../CONFIGURATION.md); the convention itself is
> [ADR-612](../adr/612-bracket-phase-id-convention.md) and the
> [compact convention card](../../gsd-core/references/phase-id-convention.md).

**`"bracket"` affects read, display, migration, and write paths:** read-path surfaces — `roadmap analyze` / `roadmap get-phase`, the W005/W006/W007 phase checks, `validate health` (including an advisory W021 covering a bracket phase's milestone disagreeing with its enclosing section, or a phase heading still spelled in legacy form and not yet migrated to bracket form), both `total_phases` derivations, state, and phase-directory membership — recognize the bracket spelling once it is set; display-path surfaces — progress, stats, manager-init, and statusline — recognize and display canonical IDs, while `progress` / `stats` expose per-phase `display_id` and keep the bare `number`. Phase-directory membership on a bracket repo scopes by the directory's real bracket token, so an artifact misfiled from another phase (`01-VERIFICATION.md` sitting in a phase `03` directory) no longer supplies `phase complete`'s pass/fail verdict for the phase it was misfiled into — the same protection legacy directories already have. Write-path surfaces — `phase add`, `phase add-batch`, `phase insert`, `phase remove`, and `phase next-decimal` — allocate or maintain canonical bracket identities in headings, directories, dependency references, renumbering, and next-token output. `phase add` / `phase add-batch` allocation counts every bracket phase of the active milestone — heading, checklist bullet, or phase directory, in this worktree or in a sibling worktree with the same `project_code` and milestone — and steps past the 999 backlog sentinel, so a new number never reuses one (#5528). `state begin-phase` and `state planned-phase` use the canonical bracket display in activity and focus fields; state writers republish the derived state contract after writes. These writes refuse missing `project_code`, an unresolved active milestone, an unrenderable phase number, unsafe or conflicting destination directories, unresolved targets for target-taking commands, and nested IDs beyond the supported depth; `phase remove` also refuses when removal would orphan owned subphases, or when a legacy-spelled directory or `Phase N:` heading the reader resolves belongs to a phase it would delete or renumber; that refusal names each spelling and the bracket form to convert it to. `phase remove` further refuses when a table row keyed by the removed id would survive outside the milestone's own Progress tables, when the active milestone lists a phase id the bracket grammar cannot represent (`02a`, `02.01.01`) at or above the removed number, or when `STATE.md`'s current phase is the removed id or one the removal renumbers; `phase add` and `phase add-batch` refuse `--id` and `phase_naming: "custom"` (their bracket precedence lands with #5067) and a located milestone window that is a decoy heading carrying the active version token ahead of the real milestone heading. Locator-backed directory lookups resolve through `resolvePhaseDirectoryLookup` and `matchPhaseDirsForLookup`, including canonical bracket IDs and migration-window legacy spellings. Call sites outside that locator path that do not resolve a convention retain the wider include-everything behavior on bracket directories: aggregate scans (`uat`, `audit`, `gap-checker`), `phase complete`'s advisory UAT/VERIFICATION warning pre-scan (which can surface a spurious warning but cannot decide completion), and the workstream inventory's per-phase completion projection (which can report a bracket phase complete or incomplete from a cross-phase stray). Existing legacy or M-NN projects can run `gsd-tools roadmap upgrade --convention bracket` to preview the conversion, then add `--apply`; the bracket target requires `project_code`, refuses a dirty tracked tree, and rolls back its own changes on failure. When a renamed phase directory's token changes, the migration also renames that phase's own artifacts inside it (`03-VERIFICATION.md` becomes `01-VERIFICATION.md`, `03-01-PLAN.md` becomes `01-01-PLAN.md`, and so on) so existing plans and verification reports remain attached to the phase under its new identity, and rewrites a `depends_on` entry inside that same directory's plan files that named a renamed sibling by its old token (`depends_on: ["03-01"]` becomes `["01-01"]`) so the dependency still resolves after migration, and rewrites that artifact's own `phase:` frontmatter scalar to its new token so `history-digest` keys decisions correctly after renumbering. Legacy sentinel phases (`Phase 999.x`/`Phase 0.x`) are lifted into their own sentinel bracket milestone rather than folded into the enclosing real milestone, and checklist bullets convert using the same reader-recognized bold-checkbox grammar `missing_phase_details` is scored against (no colon required), attributed to their own milestone section when two sections share a leading major integer. The migration refuses before writing when a source phase has no bracket spelling, a multi-milestone phase (or an out-of-section checklist bullet) has no unambiguous reader-recognized milestone section, the same legacy phase number appears twice within one milestone section, a directory matches more than one candidate heading without its slug disambiguating exactly one, two directories resolve to the same phase heading (a stale same-number copy beside the real directory), or a rename's target directory already exists and is not itself part of the same migration. The bracket write paths use this convention directly; the migration described above remains the tool for converting existing legacy or M-NN projects. A project on any other value compiles the same heading patterns and retains the same output shape it did before. **What opting in costs:** on a bracket repo a heading whose bracket is followed directly by a digit is read as a phase heading, so shapes that are legal prose headings on any other convention — `### [RFC.2119] 5:`, `### [v1.0] 2024:`, `### [ADR.612] 3:` — are claimed as phases and will move `phase_count`, `total_phases` and W006. A bracket repo cedes that heading shape; that is the trade the opt-in buys, and it is why the widened read is selected at construction time from this value rather than applied everywhere.
