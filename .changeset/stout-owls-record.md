**A plain `query dispatch-isolation` re-query no longer clobbers a degrade that mandated sequential execution, so the isolation guard stops denying the dispatch the degrade itself asked for** — two paths were affected. The #683 worktree base-check degrade is now re-derived by the resolver on every call, the way the `use_worktrees` opt-out has been since #3737, so a repo whose HEAD has diverged from its fork base keeps recording `none` across the orchestrator's own `--json` read and any subagent `gsd_run` traffic (#4222). The three dispatch sites whose degrade the resolver cannot reconstruct (the single-agent `orchestrator-worktree` fallback, the per-plan submodule intersection, `execute-plan`'s Pattern B) record it with `--force-isolation none`, and a later plain query that names no different phase or plan now holds that record while it is fresh (#4561). The two only work together because the record now states who decided it: a decision the resolver derived itself, including a degrade that overrules a `--force-isolation` value, is re-evaluated live on every query, so it does not outlive the divergence that caused it; a `caller` decision, including the execute-phase step's own final re-record, is honoured for the run; a record with no provenance, from a pre-upgrade `gsd-tools` still in flight, reads as the caller's. A project root that is not a git repository is left to the guard's #4734 fallback rather than recorded as a base-check degrade. Stdout is unchanged. The dispatch-isolation vocabulary (`harness-worktree` / `orchestrator-worktree` / `none`) and its base-check subset now have one owner, `src/dispatch-isolation.cts`, consumed by every site that can import it; the one hook-side mirror and the workflow-shell validity lists, which cannot, are pinned to it by parity tests.
