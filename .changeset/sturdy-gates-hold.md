**`query dispatch-isolation` answers `none` while it holds a sequential degrade an earlier dispatch step recorded** — for up to ten minutes after a step records `none` with `--force-isolation`, a plain query whose `--phase` and `--plan`, where it passes non-empty ones, equal the record's prints `none`, not the runtime's isolation capability. Under `--json` it marks that answer `held: true` with `decidedAt`, when the held decision was made; a query that is not holding gives `held: false`, and so does `inspect-dispatch-isolation`, which is never held. The ten minutes run from when the degrade was decided: a dispatch step that follows a held `none` re-records it with the new `--renew-held <decidedAt>` option, which does not extend the hold. A step that decides a sequential degrade itself (an `execute-plan` Pattern B segment run, the gate's orchestrator-worktree fallback) records a new `none` with its own ten minutes, so such steps run less than ten minutes apart keep a query that names no phase or plan answering `none`. A query that holds writes no decision, but it records the executor identity it derives for its own phase or plan under `.gsd/dispatch-isolation-identity/`, which the isolation guards read with the other records, so the agents that plans' `agent_hint`s route to are classified as current as after a query that records a decision; a query that cannot write that record records its decision instead of holding. The isolation sentinel gains a `decided_by` field (`caller` or `resolver`) naming who recorded the decision and a `decided_at` field recording when. **This changes the output contract of `query dispatch-isolation`:** during a hold its stdout and its `--json` `isolation` report `none` and its `harnessFlag` and `exec` are cleared, so a script that reads them as the runtime's capability should read `inspect-dispatch-isolation` instead. (#4904)
