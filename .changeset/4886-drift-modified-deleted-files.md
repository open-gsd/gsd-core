**`verify codebase-drift` now flags a map that went stale through edits** — a file modified or deleted inside a directory `STRUCTURE.md` already describes registers as a drift element (`modified` / `deleted`), counted against `workflow.drift_threshold` exactly like the four added-file categories. A file renamed or moved (with or without an edit) counts as a deletion of its old path, and a file replaced by a symlink or a submodule counts as modified. Until now only added files could produce an element: a hundred edits inside mapped directories reported `action_required: false` at every threshold, and the stale map reached the planner unflagged. An ordinary addition inside a mapped directory is still not drift (a barrel, migration or route addition counts wherever it lands, as before), and changes in territory the map never described stay out. On an actively edited repo the gate fires more often at the default threshold of 3 — that is the signal it was missing, not a new one; raise `workflow.drift_threshold` if the warn is too chatty. `affected_paths` and the `--paths` list in the warn and auto-remap messages are now filtered through the module's existing path allowlist before they are emitted: a directory prefix that is absolute, contains traversal, carries a shell metacharacter, or names the repository root (`.`) is dropped from the remediation command rather than spliced into it. A withheld prefix is not subtracted silently: it is emitted as `dropped_paths` and named on its own line in the message (#4923). When filtering withholds any prefix, `auto-remap` degrades to `warn` and no mapper is spawned, and the message says why: remapping only the surviving paths would stamp the map as current past the withheld ones, and with nothing left it would be an unscoped remap. The drift is still reported either way.
