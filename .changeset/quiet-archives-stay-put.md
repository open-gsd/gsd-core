**`roadmap update-plan-progress` now edits only the active milestone, whatever the archive's tag case, attributes or position.** Before, the active region was cut at the last literal `</details>`, so a `<details open>` wrapper around the active milestone, uppercase `<DETAILS>` archives, or archives placed after the active section either declined with `missing_phase_details` or ticked and annotated the archive instead. Archived `<details>` blocks and closed plain-heading milestone sections are now hidden for the whole edit and restored unchanged (the write seam still normalizes CRLF files to LF as a whole). A closed heading that carries the active milestone's own version (`## v2.0 Part 2 ✅`) is part of the active milestone, and the `## Progress` table inside the active milestone is the one updated, not a shipped section's own. Behaviour changes to know: a collapsed `<details>` block inside the active range (no or a non-closed `<summary>`; only a block wrapping the active milestone heading stays editable) is no longer ticked by this command, but its plan rows still count as present, so no duplicate rows are inserted. A collapsed block that holds the `## Progress` table stays editable, so the table row moves with the plan ticks. The command now declines with `archive_structure_ambiguous` and leaves ROADMAP.md unchanged when an unpaired `<details>` tag hides where an archive ends: an archive opener with a closed `<summary>` that is never closed (including a closer indented four spaces), or a stray opener ahead of a collapsed block in the active range. Archives written one-line, behind a blockquote `>` prefix, or as a closed milestone heading of any level 2-6 are hidden too; a tag indented four spaces is code and does not count. An unclosed code fence now ends at the next heading instead of hiding every later archive; the read-side milestone window keeps collapsed blocks (#3982/#1341). (#5553)
